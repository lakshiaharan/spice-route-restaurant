Problem Statement

Why Traditional Restaurant Software Fails

High Infrastructure Costs

Monolithic on-premise servers require expensive hardware and 24/7 overprovisioning even during idle non-peak hours.

Flash Rush Bottlenecks

Single servers crash during lunch/dinner meal rushes due to strict relational connection-pool limits and lack of elasticity.

Disconnected Operations

Kitchen staff, delivery drivers, and customers lack a synchronized real-time state machine for order progression.

Dietary Blindspots

Traditional menus lack intelligent macronutrient and allergen filtering, compromising diner safety and health choices.

What to Say: "Traditional restaurant monoliths suffer from high costs, flash-rush crashes, and disconnected kitchen operations."
System Design

Decoupled 3-Tier Cloud Architecture

1. Presentation Tier

Amazon S3 & Vercel Edge

  • 100% static asset offloading (HTML/CSS/JS/Images)
  • Sub-50ms global Anycast edge delivery
  • Zero CPU drain on backend compute

2. Compute Tier

AWS EC2 t2.micro (Ubuntu 24.04)

  • Stateless Node.js / TypeScript REST API
  • PM2 process supervisor for auto-restart
  • Daemonized background service on Port 3000

3. Persistence Tier

Amazon DynamoDB NoSQL

  • Single-digit millisecond read/write latency
  • Single-table partition keys (orderId, bookingId)
  • On-Demand automatic horizontal scaling
What to Say: "We physically decoupled the frontend on S3/Vercel from the EC2 compute tier and DynamoDB database."
Cloud Governance

Enterprise IAM Security & Zero-Cost Model

IAM Instance Profile Security

  • Principle of Least Privilege: Attached scoped IAM Role to EC2.
  • Zero Hardcoded Secrets: No AWS Secret Access Keys in source code or .env.
  • Automatic Token Rotation: AWS SDK fetches short-lived STS tokens via IMDS.

100% AWS Free-Tier ($0.00 / Mo)

  • Compute: AWS EC2 t2.micro (750 free hours/month covering 24/7 uptime).
  • Database: Amazon DynamoDB (25 GB free storage with 25 RCU/WCU).
  • Storage: Amazon S3 (5 GB free tier storage with public bucket policies).
What to Say: "We eliminated all hardcoded credentials using IAM Instance Profiles and achieved a 100% Free-Tier zero-cost architecture."

Viva Defense Guide (Part 1)

Databases, Security & Process Management

Q1: Why DynamoDB?

• Serverless NoSQL with single-digit ms latency.
• Eliminates connection pooling limits during peak dinner flash rushes.
• Key-value partition indexing scales horizontally on-demand.

Q2: IAM Security?

• Followed AWS Principle of Least Privilege via IAM Instance Profiles.
• SDK fetches rotating temporary credentials from IMDS.
• Zero secret keys hardcoded in source code.

Q3: Why PM2 Daemon?

• Production process supervisor keeping Node.js running 24/7.
• Auto-restarts on errors or memory spikes.
• Auto-starts service on EC2 system reboots.

What to Say: "DynamoDB scales horizontally on-demand, IAM protects credentials via IMDS, and PM2 keeps our server alive."
Viva Defense Guide (Part 2)

Decoupling, Scalability & AI Sommelier

Q4: Why S3 Decoupling?

• Offloads 100% of static asset traffic from backend CPU.
• Protects server from heavy image downloads.
• Enables sub-50ms global edge caching.

Q5: Elastic Scalability?

• Stateless backend delegates data to DynamoDB.
• Ready for Auto Scaling Groups (ASG) behind an ALB.
• Scales automatically based on CloudWatch alarms.

Q6: AI Engine?

• Multi-variable rule engine combining Boolean exclusions and calorie limits.
• Analyzes macros (Protein, Carbs, Fats) and allergen contraindications.

What to Say: "Decoupling protects backend CPU, stateless architecture enables auto-scaling, and the AI evaluates multi-variable safety."
